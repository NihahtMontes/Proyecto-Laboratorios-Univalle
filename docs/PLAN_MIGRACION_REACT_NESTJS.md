## 4. Estrategia de transición

- **Compartir SQL Server sin doble escritura**: durante la transición, NestJS opera sobre el SQL Server existente. Por cada capacidad de negocio se completa la migración de lectura y escritura a NestJS antes de iniciar la siguiente; .NET y NestJS nunca escriben las mismas tablas en paralelo. La asignación de "único escritor" por capacidad se registra mediante el protocolo de propiedad temporal de `docs/AGENT_WORKFLOW.md` y su etiqueta `LEGACY_SQLSERVER`/`NEST_SQLSERVER`/`NEST_POSTGRES` según `docs/CONTRATO_MULTISEDE.md`, sección 5. La convivencia ASP.NET/NestJS se establece en la fase 3 y el núcleo de contratos API en la fase 4.
- **Aislamiento multi-sede desde el núcleo**: la selección de tenant DB es server-side; ninguna conexión usa strings aportados por cliente; las transacciones no cruzan bases; los fallos de una sede no degradan a las demás (normativo en `docs/CONTRATO_MULTISEDE.md`, secciones 3 y 4).
- **PostgreSQL solo con estado aprobado, por sede**: cada tenant DB no se llena reinterpretando datos. Recibe una copia del estado operacional ya aprobado y conciliado de **su sede**. Los 672 conflictos V2 (528 verificaciones y 144 mantenimientos, con huella de mapeos `E3766F21F530C2CC3252FED74B11700D7A1BDD267FE29F6DC439A611298EA4CC` según DATA-002) siguen requiriendo decisión por fila; no se automatiza, no se promedia y no se acepta globalmente. Su reconciliación ocurre en la fase 11.
- **Pipeline histórico congelado en su lugar**: `Tools/HistoricalDataImport/` y `Tools/HistoricalDataApply/` permanecen sin cambios y en su fuente actual hasta certificar la carga final. Portarlos a Node es una decisión separada, condicionada a que sigan en uso; se decide en la fase 10.
- **Migraciones EF existentes intocables**: ninguna migración existente se modifica (regla de `AGENTS.md` y `context.md`). El esquema nuevo para PostgreSQL se diseña aparte y no reutiliza migraciones EF.
- **Excel original protegido**: `D:/proyectoSis/Excels/Plantilla_Original.xlsx` no se mueve, edita ni versiona; se verifica su SHA-256 (`FAEAF00640BD4AF05D78C22B3B5FB7E105260BF8AF8A4B5E8FC2FAD4A78484A4`, verificado el 9-09-2026 en `docs/AGENT_WORKFLOW.md`) antes y después de cualquier tarea que lo use. Si difiere, se detiene todo y se reporta el incidente.
