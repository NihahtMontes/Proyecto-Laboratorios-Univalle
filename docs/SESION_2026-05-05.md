## 2. Módulo L-6: Verificación Masiva

### 2.1 Problema Original

El L-6 anterior requería verificar equipos **uno por uno** con un checklist extenso de 13 puntos (VerificationCheckItems). La ingeniera solicitó cambiarlo a:
- Verificación **masiva por laboratorio**
- Solo marcar **PhysicalCondition** (Excellent/Good/Regular/Bad/Decommissioned)
- Si Bad → modal con observaciones → auto-crear L-7
- Sin checklist, sin VerificationCheckResults

### 2.2 Arquitectura

Se creó una nueva página `MassCreate` completamente independiente del `Create` individual.

**Flujo:**
```
Wizard Step 1 → [Verificación Masiva por Laboratorio]
  → /Verifications/MassCreate?isWizard=true&labId=X
  → Tabla con dropdowns de condición por equipo
  → Bad → modal Bootstrap para observaciones
  → Guardar → N Verifications + N Requests L-7 (para Bad)
  → Actualiza ManagementPlan.CurrentPhase
```

| `Pages/Verifications/MassCreate.cshtml.cs` | PageModel: OnGet (carga labs), OnGetEquipmentByLab (AJAX), OnPost (guarda masivo) |

### 2.4 Archivos Modificados

| Archivo | Línea(s) | Cambio |

| `Pages/Requests/Create.cshtml.cs` | 44-47 | Puente L-6→L-7: `Faults` → `Observations` |

### 2.5 Reglas de Negocio

- Un equipo solo aparece en MassCreate si `CurrentPhase == Verification && VerificationId == null`
- Si PhysicalCondition es **Bad** → Crea Verification (WithObservations) + Request L-7 automático
- Si PhysicalCondition es **Good/Regular/Excellent** → Crea Verification (Completed), avanza plan a Maintenance
- Si PhysicalCondition es **Decommissioned** → Crea Verification, avanza plan a Maintenance
- El contador `CountL6` y `Step1Plans` ahora excluyen equipos que YA tienen `VerificationId` asignado

## 3. Módulo Correctivo

### 3.1 Problema Original

El sistema solo soportaba mantenimiento **preventivo** (planificado por semestre). La universidad necesitaba un flujo separado para **correctivos** (fallas imprevistas) que:
- No requiere L-6 (verificación)
- No requiere sincronización masiva de equipos
- Empieza directamente en L-7 (reporte de falla)
- Usa el mismo wizard para L-8, L-3, Kardex, L-12
- Tiene su propio dashboard, métricas y listado

### 3.2 Evolución de la Solución (3 Intentos)

#### Intento 1: `isCorrective` en el Wizard
**Qué se hizo:** Se agregó una variable `isCorrective` al Index y a los Create pages. Se intentó condicionar la UI del wizard (ocultar Step 1, 5 burbujas).

**Por qué falló:** El wizard usa `GetCurrentManagementAsync()` que retorna una gestión al azar cuando hay 2 activas (preventiva + correctiva). El `isCorrective` se evaluaba sobre esa gestión aleatoria → a veces true, a veces false.

#### Intento 2: `ManagementId` en todas las rutas
**Qué se hizo:** Se agregó `ManagementId` como query param en Index.cshtml.cs y en todos los "Volver al Wizard". Se creó `ResolveManagementAsync()` en Requests/Create.

**Por qué falló:** Las **entradas** al wizard (Details.cshtml → "Iniciar Ronda" / "Reportar Falla Crítica") no pasaban `ManagementId`. Los KPI cards tenían URLs hardcodeadas sin ManagementId. Los 5 Create pages llamaban `GetCurrentManagementAsync()` sin tipo en su `OnGetAsync`.

#### Intento 3: `ManagementType` + Sidebar + Tabs (SOLUCIÓN FINAL)
**Qué se hizo:** Se creó el enum `ManagementType` (Preventive=0, Corrective=1) en el modelo `Management`. Se separaron físicamente las gestiones en BD. Se reorganizó el sidebar y la página de Gestiones con pestañas.

### 3.3 Errores Encontrados y Corregidos

#### Error 1: Burbuja L-6 visible en wizard correctivo
**Causa:** `_WizardSteps.cshtml` usaba array fijo de 6 pasos. En correctivo, el wizard entra en Step 3 pero el stepper muestra L-6 como completado.

**Corrección:** `_WizardSteps.cshtml` ahora recibe `ViewData["IsCorrective"]`. Si true, usa array de 5 pasos (L7-L12) y ajusta step numbers (burbuja 0 = Step 2).

```csharp
// _WizardSteps.cshtml
var isCorrective = (bool)(ViewData["IsCorrective"] ?? false);
var steps = isCorrective
    ? new[] { "L7 Solicitud", "L8 Mantenimiento", "L3 Salida", "Kardex", "Desembolso" }
    : new[] { "L6 Verificación", "L7 Solicitud", "L8 Mantenimiento", "L3 Salida", "Kardex", "Desembolso" };
int stepNumber = isCorrective ? (i + 2) : (i + 1);
```

#### Error 2: Rutas sin ManagementId
**Causa:** 6 lugares críticos no pasaban `ManagementId`:
1. `Details.cshtml` "Iniciar Ronda" → `/Index?ShowWizard=true`
2. `Details.cshtml` "Reportar Falla Crítica" → mismo problema
3. 5 KPI cards (L6, L7, L8, L3, Desembolso) → URLs hardcodeadas
4. `Index.cshtml` "Reportar Nueva Falla Crítica" → `/Requests/Create?isWizard=true`
5. `Index.cshtml` "Volver al Dashboard" → `/Index?ShowWizard=false`
6. `_WizardStep` action links → sin ManagementId

**Corrección:** Agregar `asp-route-ManagementId="@Model.Management.Id"` o `&ManagementId=@Model.Management.Id` a cada URL.

#### Error 3: Dropdowns bloqueados en L-7 correctivo
**Causa:** `Requests/Create.cshtml` líneas 48, 65, 82 usaban `@if (isWizard)` para bloquear los selects de Facultad/Lab/Equipo. En correctivo, `isWizard=true` pero no hay ManagementPlan preexistente que fije los valores.

**Corrección:** Cambiar condición a `@if (isWizard && !isCorrective)`.

```html
<!-- ANTES -->
@if (isWizard) { <select ... disabled> }
<!-- DESPUÉS -->
@if (isWizard && !isCorrective) { <select ... disabled> }
```

#### Error 4: Redirect post-save a gestión equivocada
**Causa:** `Requests/Create.cshtml.cs:136` llamaba `GetCurrentManagementAsync()` sin tipo. Con 2 gestiones activas, retornaba cualquiera.

**Corrección:** Usar `ResolveManagementAsync()` que busca primero en `ManagementPlanId`, luego en `ManagementId` query param, y solo como último recurso llama `GetCurrentManagementAsync()`.

#### Error 5: Delete bloqueado para gestión activa correctiva
**Causa:** `Managements/Index.cshtml.cs:105` bloqueaba `Status == Active` para cualquier tipo.

**Corrección:** Agregar excepción `&& management.Type != ManagementType.Corrective`. También se movió el redirect de éxito dentro del try y se agregó `Type` al redirect para preservar la pestaña.

```csharp
if (management.Status == ManagementStatus.Active 
    && management.Type != ManagementType.Corrective)
{
    TempData.Error("No se puede eliminar una gestión activa.");
    return RedirectToPage("./Index", new { Type = type });
}
```

#### Error 6: Acentos rotos en SweetAlert2 (`gesti&#xF3;n`)
**Causa:** `_Layout.cshtml` líneas 176, 187, 199 usaban `@TempData["Error"]` dentro de strings JavaScript. El motor Razor aplicaba HTML-encoding y `gestión` se convertía en `gesti&#xF3;n`.

**Corrección:** Envolver con `@Html.Raw()`:

```javascript
// ANTES
title: '@TempData["Success"]'
text: '@TempData["Error"]'

// DESPUÉS
title: '@Html.Raw(TempData["Success"]?.ToString() ?? "")'
text: '@Html.Raw(TempData["Error"]?.ToString() ?? "")'
```

#### Error 7: Semester 0 bloqueado en Edit
**Causa:** `Managements/Edit.cshtml.cs:43` validaba `[Range(1, 2)]`. La gestión correctiva tiene `Semester = 0`, por lo que `ModelState.IsValid` fallaba silenciosamente y el Edit nunca persistía cambios.

**Corrección:** Cambiar a `[Range(0, 2, ErrorMessage = "Semestre inválido (0, 1 o 2)")]`.

## 4. L-48 / Cronograma de 8 Semanas

### 4.1 Filtros Corregidos

**Problema:** El filtro "Todos" mostraba equipos `VerifiedGood` (Activos Sanos) que tienen su propia pestaña. Los filtros Planeado/Progreso/Ejecutado usaban lógica incorrecta (fases del wizard en vez de semanas).

**Corrección en `Details.cshtml.cs` líneas 236-264:**

| Filtro | Antes | Ahora |
|--------|-------|-------|
| Todos | Sin filtro (incluye sanos) | `CurrentState >= AwaitingRequest` |
| Planeado | `CurrentPhase > Maintenance` | `PlannedWeek != null` |
| En Progreso | `CurrentState >= AwaitingRequest && CurrentPhase <= Maintenance` | `Maintenance.Status == InProgress` |
| Ejecutado | `PlanStatus == Completed` | `ExecutedWeek != null` |
| Externo | `ServiceType == External` | Sin cambios |

### 4.2 Regla Verde ≥ Púrpura

**Problema:** Se podía marcar Ejecutado (verde) sin haber marcado Planeado (púrpura) primero. Se podía poner una semana ejecutada menor que la planeada.

**Corrección en `Details.cshtml.cs` línea 345-358:**

```csharp
else if (type == "executed")
{
    if (plan.ExecutedWeek == weekNumber)
        plan.ExecutedWeek = null;
    else
    {
        if (plan.PlannedWeek == null)

        if (weekNumber < plan.PlannedWeek.Value)
            return new JsonResult(new { success = false, error = "La semana ejecutada no puede ser menor que la planeada." });

        plan.ExecutedWeek = weekNumber;
        // ...
    }
}
```

## 6. Dashboard / Wizard

### 6.1 Contador L-6 Corregido

**Problema:** `CountL6` y `Step1Plans` contaban equipos con `CurrentPhase == Verification` pero sin verificar `VerificationId`. Un equipo que YA tenía verificación pero seguía en fase Verification se contaba doble.

**Corrección en `Index.cshtml.cs`:**
- Línea 148-154: Agregar `p.VerificationId` a proyección `allStats`
- Línea 170: `CountL6 = allStats.Count(p => p.CurrentPhase == WizardPhase.Verification && p.VerificationId == null)`
- Línea 276: `Step1Plans = ActivePlans.Where(p => p.CurrentPhase == WizardPhase.Verification && p.VerificationId == null)`

### 6.2 Completados

**Problema:** `EquiposTerminados` usaba `PlanStatus == Completed` (flag administrativo). Un equipo en fase 2 (L-7) con `PlanStatus=Completed` se contaba como terminado.

**Corrección en `Index.cshtml.cs:157`:** `EquiposTerminados = allStats.Count(p => p.CurrentState == WizardEquipmentState.Completed)` — solo equipos que llegaron a L-12.

### 6.3 Wizard Steps Dinámico

**Problema:** El stepper usaba array fijo de 7 pasos con skip condicional `if (i == 1) continue`. Los números de los círculos no coincidían.

**Corrección en `Index.cshtml:7-11,424-441`:** Array dinámico + step numbers calculados con `stepNum = isCorrective && i > 0 ? i + 1 : i`.
